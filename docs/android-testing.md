The earlier published foundation and its passing workflows are recorded below as historical evidence. This follow-up extends the current `main` checkout with a runtime web-to-API proxy and a direct Android BLE/GATT adapter. The BLE debug APK tested on physical devices was built from source commit `887645de142f4f1eff7282d4f9434a94d81e1cd8` and has SHA-256 `d7a40d98897fe49a224fa575a56012860147ee55343a75ef182d64feb7a30cd8`; the matching local and installed hashes were verified on both phones. This physical result is limited to code-confirmed pairing and acknowledged text messages with Wi-Fi disabled; it does not establish automatic failover, range, battery or background behavior. The two-device proof can be repeated with [the local BLE runner](../scripts/android-ble-dual-test.mjs).

## Physical Nearby product result

Completed at **21:23 IST on 5 October 2026**. Instrumentation elapsed 76.459 seconds on the S24 and 76.145 seconds on the tablet. The original author disconnected before the carrier synchronized. The returned receipt verified the original envelope hash; relay metadata recorded one peer hop without replacing its author signature.

A 4 MiB generated text fixture used 512 encrypted 8 KiB chunks. The receiver persisted at least 32 chunks before deliberate disconnect. Re-pairing and reoffering resumed the bitmap, verified the complete SHA-256 and returned a durable file acknowledgement. The urgent signed event arrived before resumed attachment completion.

USB supplied fixture barriers and access to the local API. All peer messages, chunks, events and receipt-return bytes traveled through the product's actual Nearby adapter. The test verified `internetValidated=false` on both devices at preparation and all three connections; USB API access is not an independent internet proof. Barrier timing metadata measures the difference between peers arriving at a fixture barrier, not radio latency or throughput. No range or battery claim follows from this short run.

## Physical Bluetooth-only result

The final development APK passed `NativeBleDualTest` on the Galaxy S24 (SM-S921B, Android 16/API 36) and Galaxy Tab S9 (SM-X510, Android 16/API 36). S24 was the author/initiator; the tablet advertised. The test compared the six-digit codes generated by both BLE adapters before accepting the link. Wi-Fi was disabled on both; the instrumentation independently asserted Wi-Fi off and no validated internet. BLE/GATT carried the actual Swarm HELLO, message, and acknowledgement frames in both directions; USB loopback supplied only the ephemeral code-comparison and role barriers. The test completed in 4.992 seconds on the S24 and 4.946 seconds on the tablet.

Both installed `org.saathi.android.dev` APKs matched the local artifact hash above. The test also asserted that BLE does not advertise file transfer or calls. It did not test automatic Nearby-loss recovery, participant-key continuity across transports, attachment retry, Android background/lock behavior, distance, battery use, or other Android models. The original settings were restored after the run: Wi-Fi and Bluetooth on, the S24's 10-minute timeout and the tablet's 30-minute timeout unchanged, and the temporary charging-awake override removed.

## Physical three-peer relay

Completed at **22:19 IST**, 5 October 2026 (16:49:24.594 UTC). S24 instrumentation elapsed 83.699 seconds; tablet 82.860 seconds. A was the physical S24 author, B the physical tablet carrier, and C a fresh Saathi Chromium profile on the Windows computer. The S24 disconnected before B paired with C. C received the same signed envelope at **two peer hops**, verified its unchanged hash, explicitly enabled carrier consent and obtained a signed `PUBLISHED` receipt from the isolated API. C re-paired with B to return that receipt; B later re-paired with A and returned it to the original author. All assertions passed on both Android devices.

Native peer data and browser peer data used actual local Wi-Fi WebRTC; USB only coordinated fixture barriers/invitations and supplied the native local API path. ## Reproduce approved two-device tests

Build using the development trust directory and run the local fictional API before testing. Select the two explicitly approved model names:

```powershell
node scripts/android-dual-test.mjs SM-S921B SM-X510 nearby
node scripts/android-dual-test.mjs SM-S921B SM-X510 wifi
node scripts/android-dual-test.mjs SM-S921B SM-X510 wifi browser
node scripts/android-browser-test.mjs SM-X510
```

The Wi-Fi commands need a reachable shared Wi-Fi/hotspot and use actual microphones/cameras briefly. They check received audio bytes and decoded video frames without recording streams. The optional browser third peer also requires the built web app at localhost:3000 and the tablet-scoped host UDP rule. The helper grants only app runtime permissions used by the selected scenario and keeps its fixture activity awake. It does not change the owner's global screen timeout. Do not run another installer or instrumentation runner concurrently on either selected device.

For the direct BLE proof, build `:app:assembleDebug :app:assembleDebugAndroidTest`, turn Wi-Fi off on both phones while leaving Bluetooth on, then run `node scripts/android-ble-dual-test.mjs` from the repository root. The runner selects the S24 and Tab S9 by model, installs the debug artifacts, and coordinates only synthetic test barriers over an authenticated loopback server exposed through ADB reverse. It does not change Wi-Fi, Bluetooth, or screen timeout settings. Keep the devices unlocked and do not start another instrumentation task during this test.

Optional fixture tests require a development build, locally supplied arguments and the fictional `android-volunteer@saathi.test` account. No credential is embedded in an APK. Unique fixture storage scopes preserve ordinary product records; registered fixture identities are revoked during cleanup. Local raw serials, networking descriptions, credentials and UI dumps remain ignored. Public documentation contains only sanitized scenario results.

Repository reopening proves persisted bytes/identity, not process death. The separate emulator force-stop test proves its draft's actual process recovery. Standalone CI secure-storage tests skip API/browser/dual fixtures without their explicit arguments.

# Native Android architecture

The app is now **CJP Swarm**, displaying **SWARM by CJP**, with configurable build branding and compatible existing package/storage/protocol IDs. Updates and Needs retain authoritative relief semantics; Chats/Nearby add a separately signed participant/membership domain. The communication preview is enabled only in development/QA; private chat remains disabled in release pending independent security review. [Chat/channel architecture](chat-channel-architecture.md) records identity, membership, JOSE encryption, receipts, authorized history/relay, retention, attachment quotas and experimental limits. The public web/API remains separate from operational private chat.

The product lives in `apps/android`; `spikes/android` remains the isolated transport measurement probe. Package IDs are `org.saathi.android.dev`, `org.saathi.android.qa` and `org.saathi.android` for development, staging and production. Version 1.0.0/code 1 targets SDK 36, compiles against 37 and supports SDK 26+. Android 8 is a deliberate compatibility floor for Keystore, modern TLS and maintained WebRTC; installing on an old unpatched OS does not provide current OS security. API 26 compatibility is checked by lint and still needs older-device execution.

Kotlin/Compose was selected over React Native to keep radio permissions, Android Keystore, lifecycle and media ownership within one native runtime. The web/API/domain foundation remains TypeScript. Wire compatibility is tested with real TypeScript-generated canonical JSON/P-256 signatures; Kotlin does not own separate request or donation semantics. Material 3 navigation adapts from a phone bottom bar to a tablet rail. Local Manrope/Lora fonts preserve the existing Saathi identity. Their upstream Google Fonts OFL licenses ship in app assets.

`Repository` owns verified service configuration, origin-scoped encrypted cookies/CSRF, public snapshots, preparation, original-author events and signed receipt verification. `SecureStore` uses SQLite with per-record AES-256-GCM, random IVs and bucket/ID authenticated data. The AES key and each account's P-256 private signing key live in Android Keystore. StrongBox is attempted for signing, with platform fallback; the UI reports actual storage protection, rather than promising hardware on every device. Backup and device-to-device extraction exclude the app's private data.

`SaathiViewModel` owns foreground jobs and action/error state. Calls end when the activity leaves the foreground; background calling/relaying is not advertised. Discovery is an explicit 60-second window with a ten-second retry backoff. A 30-second foreground health check distinguishes backend reachability from saved information. Critical signing saves the draft first, closes the form only on success and persists the original signed event before any transmission. Public refreshes replace snapshots atomically; freshness remains visible offline.

`PeerSession` provides bounded durable messages, event fragmentation, original-signature relay and receipt return. A bounded priority queue favors structured events over text/status and file chunks. Frames are limited to 24 KiB; sessions keep at most eight incomplete envelopes, 500 messages and 500 events. Confirmation is a connection check, never proof of current volunteer authority. Old queued frames are scoped to a connection generation and are not deliberately replayed to a new person.

The capability-driven transports are optional GMS Nearby Connections for native bytes, direct Android BLE/GATT for small foreground messages and structured updates, and independent manual local-IP WebRTC for the browser bridge and calls. These transports do not create a simultaneous global mesh. Nearby uses temporary random Saathi names and explicit same-code confirmation. BLE uses a transient random advertising token, an encrypted bonded GATT link and a six-digit code that both people must compare and accept; automatic Nearby-to-BLE recovery keeps the signed peer identity and only retries messages addressed to that same verified participant. BLE does not carry files, photos, calls or other large payloads; those remain saved until a stronger transport is available. WebRTC uses no ICE/signaling servers: users exchange expiring, bounded invitations on an existing reachable local network and compare a fingerprint-derived code. Wi-Fi Direct/Aware and hotspot creation are not implemented. Future iOS may reuse envelopes, receipts, capabilities and sync semantics; there is no iOS implementation or device-support claim.

`CommunityRepository` gossips signed internet-gateway leases during confirmed peer sessions. A lease expires after 120 seconds; advertisements retain at most 16 routes and 16 hops. These are reachability hints for status, not a source-routed end-to-end path. Eligible signed public help/update events can be carried over later encounters, with event deduplication, expiry and a 16-hop ceiling. A node learns which gateway was recently reachable only as this information arrives through encounters, so status can be stale or absent. Each Android client has one active nearby peer connection: this is opportunistic asynchronous store-carry-forward, not simultaneous broadcast. An offline event reaches the server only if it is carried through encounters to a phone with validated internet that has opted into relay before the event expires and exhausts its hop budget. Relay settings, battery/data controls and the 5 GB daily cap still apply; only the allowed public event/media flow is uploaded, not private chat. Two-device tests do not prove three-device forwarding, 1,000-device reach or a delivery-time guarantee.

Native-to-native attachments negotiate up to 16 MiB through signed feature policy; browser interoperability retains 1 MiB. Files require recipient consent, 8 KiB encrypted chunks, a complete SHA-256 check, explicit retry/cancel, 128 MiB local quota, free-space reserve and a 20% battery/charging guard for larger files. Reoffering uses the received-part bitmap. Calls pause file transfers; urgent events and messages remain available. Incoming media stays disabled until acceptance. Video reduces bitrate/frame rate/resolution on weak statistics and pauses after sustained weakness to preserve audio. Real range, battery and audio-continuity measurements remain release gates.

Ordinary writes persist an encrypted original body and idempotency key before network transmission. Retry from Saved reuses both after an uncertain response or restart; a changed body is refused. Offline messages can be composed before pairing and explicitly resent to the currently confirmed person. Sign-in recovery uses the same account without deleting prepared work. Saved work offers scoped removal confirmations; uncertain ordinary writes must be resolved before their retry identity can be removed.

Primary destinations are Updates, Chats, Nearby, Needs and More. More retains the team portal, saved relief work and connection fallback. DMs/channels use stable IDs independent of the current transport, with durable private drafts and truthful Saved/Sent/Delivered/Read. The app also exposes completed needs, request verification, reservations/orders, volunteer preparation, request/field drafts and signed updates, delivery confirmation and prepared-device revocation. Verified attachments export through Android's document picker after a complete hash check; the chosen copy leaves private app storage. Coordinator/admin management and native field-photo authoring remain the existing operational web portal; chat media is not silently published by nearby transfer or Create Need.

Verified results and unproven scenarios are tracked separately in [Android testing](android-testing.md). See [service trust](adr/0003-signed-service-configuration.md) and [release setup](android-release.md).

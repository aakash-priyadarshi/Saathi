# CJP Swarm conversations

This milestone extends the existing native product and transports. The app/store name is **CJP Swarm**, with **SWARM** and **by CJP** as the visual identity. The existing Saathi relief protocol, package IDs, database and secure-storage names remain compatible with installed work. The public website remains the relief/publication surface, not a private chat portal.

## Decisions and implementation contract

The current QA implementation admits up to **200 members per channel**, while
retaining 16 joined channels per identity and one active native peer link. See
[ADR 0011](adr/0011-two-hundred-members-and-walkie-talkie.md) for roster budgets,
fragmentation, sparse encounter forwarding and the separate direct-chat
walkie-talkie control. It is not a 200-device simultaneous mesh or live call.
See [field connectivity](field-connectivity.md) for direct Android pairing,
hotspot guidance, Bluetooth fallback and the battery strategy.

Chats are identified by participants or a channel ID, never a radio session. A direct conversation hashes the two stable participant key fingerprints in sorted order. Channels have explicit random IDs and an owner; no automatic partition-specific General rooms are created. Updates and official relief events remain separate from private conversation. Chat ownership gives no volunteer/coordinator authority.

Chat identities use a separate non-exportable signing key and a display name chosen locally. Profiles sign their public encryption key; names alone do not prove a person's identity or humanitarian role. Contact fingerprints are established through the existing matched-code pairing. Discovery is opt-in, bounded and advertises only a chosen name or temporary label. Only the confirmed current path counts as live reachability; stored contacts and relayed history do not inflate it. The current adapters retain one live peer session at a time.

Private payloads use standard JSON Web Encryption, through maintained JOSE implementations: ECDH-ES/A256GCM for recipient-bound direct messages and channel-key envelopes, and dir/A256GCM for invite-only channel content. Signing retains the existing RFC 8785/P-256 construction. Encryption private material is protected by the existing Android Keystore AES storage key; the separate signing key stays non-exportable. This is not Signal/MLS, has no forward-secrecy claim, and needs independent cryptographic review before sensitive operational use. See [JWE](https://www.rfc-editor.org/rfc/rfc7516.html) and [Nimbus examples](https://connect2id.com/products/nimbus-jose-jwt/examples).

Channel policy is owner-signed, versioned and time-bounded. It defines membership and roles independently from humanitarian RBAC. Open discovery exposes minimal descriptors; full policy is provided when needed for joining/author validation. Invite-only channels are absent from general discovery. Invitations to a known participant are signed, expiring and bound to that participant's key. Channel managers can also create a single-use, expiring join link. The first request received by the channel owner reserves it for review; request delivery may wait until devices meet. A channel manager must approve before a fresh membership policy and encryption key are issued. The link contains no channel roster or key and does not grant access by itself. Reopening an already accepted recipient-bound invitation is idempotent. Removal increments policy/epoch and excludes the removed member from fresh key envelopes. Existing members can retain messages they previously saw; offline peers cannot learn an unseen revocation immediately. Expired policy stops new channel sends until refreshed. Stale or conflicting policy cannot replace a newer accepted version.

The owner authorizes membership; an open join can wait while the owner is absent. Eligible messages remain in the same conversation when using server sync or nearby transport. Stable message IDs and envelope hashes reject equivocation and deduplicate different routes. Receiver-signed delivery confirmation differs from carrier transport acknowledgement or server storage. Private messages never use Published. Author sequence plus bounded local display times give deterministic ordering without treating device clocks as membership authority.

Retention, bounded inventory, explicit history eligibility and the existing priority queues prevent indiscriminate history flooding. Urgent relief events remain priority zero; chat text/state precedes file chunks. Blocks and mute use participant/conversation IDs, not transport names. Attachment consent, hashes, resumption, storage and battery limits stay in the current file subsystem; private chat attachments must not enter the public field-media pipeline. Recording/playback is foreground-owned and never starts from discovery.

Synced chat has its own operational handler and database tables. Signed requests authenticate the chat participant without conferring relief permissions. The public API deployment exposes no chat history. The server checks current membership, revocation, stable IDs, expiry, bounds and blocks before storing or returning messages. Stored private content remains ciphertext; server metadata is not secret. Offline acceptance may later be rejected by authoritative current policy, with Needs attention rather than a false delivery claim.

## Product and motion

Native navigation becomes Updates, Chats, Nearby, Needs and More. More contains saved relief work, identity/privacy and the existing team portal. Conversation rows show people/channel names, preview, time, unread/mute and truthful delivery. Calls live in a DM when the confirmed path actually supports the measured native media capability. Huddles and group video remain unavailable until implemented and measured.

Keep the paper/forest palette, Lora headings, Manrope controls and Material phone/tablet affordances. Functional motion uses [Compose animations](https://developer.android.com/develop/ui/compose/animation/quick-guide). One bounded Swarm formation explains a confirmed connection; navigation/status, new messages and attachment progress use quiet transitions. No permanent radar loop, invented reachable people or animated delay before controls work. Remove animations uses an intentional static/instant path. Rive/Lottie are optional future asset runtimes, not required dependencies for effects Compose can express directly.

## Evidence tracking

The implementation extends source `d60cdaf`. Shared/API validation records 26 unit tests, 45 real PostgreSQL integration tests and all 14 browser regression cases; native validation records nine JVM tests. New chat store-close/reopen instrumentation and the three existing SecureStore cases passed on both Samsung devices and the emulator. This is a storage reopen proof, not an Android process-death or reboot proof for chat.

The [two-device chat record](benchmarks/android-chat-nearby.json) covers physical S24/tablet matched-code radio pairing, one stable encrypted DM, signed Delivered/Read, server/radio deduplication, owner-approved open membership, recipient-only invitation/replay, private-channel messages, generated photo and synthetic AAC transfer, encrypted interrupted 4 MiB resume, server ciphertext upload/download, removal and blocking. Both devices reported validated internet at each network checkpoint. It proves radio/server route continuity; it does not prove a complete internet → offline → internet transition. Step milliseconds are coordinator barrier intervals, not general latency/throughput measurements. See [Android testing](android-testing.md) for exact scopes and outstanding cases.

## Current implementation limits

Development and QA enable the communication preview. Release builds keep it disabled pending independent security review. No production rollout or Railway deployment is implied. The signing key is non-exportable; the separate static ECDH private key is software-generated and encrypted at rest with Android Keystore AES. Static recipient/channel encryption does not provide forward secrecy or post-compromise recovery. Open channel payloads are readable by authorized members and the operational server; invite-only payloads and DMs are ciphertext there.

The policy roster has at most 16 entries, including removed entries. Policies last at most six hours, and owner renewal changes epoch/key wraps. Owner-signed policy remains the membership/key authority. Five roles have explicit capability ceilings; delegated Admin/Moderator actions, threads, announcements, locks, report review, hide and stable-identity bans now enforce those ceilings locally and on raw server input. An owner approves open joins. Auto-admission invite links retain signed recipient-bound policy in bounded gzip/base64url. Approval-required invitations instead carry a key-free signed recipient descriptor, then explicit review/request and fresh owner policy. QR is shown within the existing size budget; bounded local camera scan preserves manual fallback. Larger invitations use share/copy/direct-nearby links and require recipient confirmation.

Native persistence caps each chat bucket at 500 records, channel selections at 16, files at 50 and aggregate attachment bytes at 128 MiB. Messages expire after seven days. Inventory/history is bounded and authorized. Earlier private history is available only to identities included in that epoch. Channel carriers can forward eligible signed messages at up to six hops; unrelated DM carriers are not supported. A receipt from one channel recipient does not mean every member read the message. Receipts bind the exact original envelope hash.

Attachments use random per-file AES-256-GCM keys, a 12-byte nonce and AAD `SWARM_ATTACHMENT_V1/{attachmentId}`. Plaintext is limited to 16 MiB minus nonce/tag overhead. The key/name/MIME/plaintext hash travel in the conversation payload; the radio file layer carries opaque ciphertext and its hash. Consent, resumed bitmaps, storage/battery limits and priority-zero relief events reuse the existing subsystem. Export/playback/preview verify ciphertext and plaintext. Photo previews decode off the UI thread at a bounded size. Voice notes use foreground AAC recording with a two-minute cap; synthetic AAC transfer evidence is distinct from microphone-recording proof. Leaving the foreground discards unfinished recordings and stops playback/calls.

The operational `/chat/attachment` handler stores ciphertext in PostgreSQL, separate from public media processing. An original-author signed manifest binds attachment ID, original message hash, ciphertext size/hash and expiry. Every signed upload/download rechecks current membership, historical private-epoch eligibility, blocks and expiry. Six 8 KiB chunks per request support resume and conflicting-part rejection. Quotas reserve at most 50 files/64 MiB per author and 512 MiB globally for this experimental database-backed path. Maintenance/request cleanup deletes expired ciphertext. This is bounded experimental storage, not a scalable production object-store claim. Plaintext keys never enter the manifest. Foreground checks move one batch automatically; explicit sync continues without holding the chat mutex.

Notifications currently mean batched in-app unread/mention notices and unread counts; mute suppresses them. There is no push or background-delivery guarantee. Search covers held local messages. Group audio/video is unavailable. Live voice/video reuses the measured native local-Wi-Fi adapter and ends on foreground loss. No generalized internet calling service is introduced. The browser retains public relief and version-1 local exchange; new private-chat browser interoperability is not enabled.

Signed sync requests carry timestamp/nonce and a server timestamp high-water mark. Exact retries return a cached response without reapplying blocks/membership. Reused IDs with different content and older/equal-timestamp new requests are rejected. Sorted transaction locks protect profiles, conversations and duplicate IDs. Transport changes do not change conversation IDs. Clearing local copies differs from deleting shared history: synchronized history may return.

Previous transport tests remain evidence at their recorded scope. Three Android devices are unavailable, so new three-native-peer chat relay is not physically verified; logical three-participant membership/history/relay authorization has database coverage. Android-browser tests, no-internet calls, permission/lifecycle/range/battery/lock tests, actual microphone recording and video attachment transfer remain attended test gates. Synthetic voice transfer does not prove microphone recording. No previous result is promoted to private-chat security certification.

# Nearby connectivity research

Research date: 5 October 2026. Physical devices available to the owner: Android only. This workstation can test Chromium processes, persistent browser storage and the canonical API. Phone radio, range, battery, OEM power management, screen lock and iOS results must remain **not tested** until measured on hardware. Documentation support is not a Saathi compatibility claim.

## Findings from primary sources

1. WebRTC provides encrypted data channels and audio/video tracks; signaling is application-defined. Local host candidates can work without STUN/TURN when peers have a reachable network path. A shared SSID does not guarantee reachability: client isolation, VPNs, firewalls and hotspot implementations can prevent it. A pairing code alone cannot discover the other endpoint without an exchange channel. [W3C WebRTC](https://www.w3.org/TR/webrtc/), [peer connections](https://webrtc.org/getting-started/peer-connections), [data channels](https://webrtc.org/getting-started/data-channels).
2. Browser camera/microphone capture requires a secure context, user permission and an allowing Permissions Policy. It does not intrinsically require internet once the secure-origin application is loaded. Offline capture still depends on browser/OS lifecycle and permission state. No capture starts merely because a peer connects. [W3C Media Capture](https://www.w3.org/TR/mediacapture-streams/).
3. Android Wi-Fi Direct exposes native discovery and socket connectivity; it requires runtime permissions on recent releases. It is not a browser API or an iOS interoperable networking contract. Android local-only hotspots create a network without internet; Android 13+ requires Nearby Wi-Fi permission. Joining, enabling radios and permission prompts require supported OS flows. [Wi-Fi Direct](https://developer.android.com/develop/connectivity/wifi/wifip2p), [local-only hotspot](https://developer.android.com/develop/connectivity/wifi/localonlyhotspot), [Wi-Fi permissions](https://developer.android.com/develop/connectivity/wifi/wifi-permissions).
4. Android applications targeting Android 10+ cannot toggle Wi-Fi through `setWifiEnabled`; use a system settings panel. Recent Bluetooth APIs likewise restrict silent enable/disable. Never treat a permission grant as evidence that a radio is enabled. [Android Wi-Fi controls](https://developer.android.com/about/versions/10/privacy/changes#enable-disable-wifi), [BluetoothAdapter](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter).
5. Google Nearby Connections supplies native discovery, authenticated encrypted connections and bytes/files/streams, selecting among Bluetooth/BLE/Wi-Fi internally. There are Android and Swift SDKs. The Android Play-services dependency and usage analytics are relevant; a non-GMS fallback is still needed. Its actual Android/iOS combinations and media behavior need device testing. It is useful for event/file exchange, not automatically a WebRTC-compatible browser network interface. [Nearby Connections](https://developers.google.com/nearby/connections/overview), [Swift discovery](https://developers.google.com/nearby/connections/swift/discover-devices).
6. A newer alternative must be included: iOS 26 Wi-Fi Aware on supported hardware, including iPhone 12+, offers standardized peer-to-peer Wi-Fi and app-to-app pairing through DeviceDiscoveryUI. Android has Wi-Fi Aware APIs from API 26 but hardware/firmware support and available data paths vary. Cross-platform interoperability is a candidate to measure, not something to infer from the shared standard. [Apple Wi-Fi Aware](https://developer.apple.com/documentation/wifiaware), [Apple WWDC25](https://developer.apple.com/videos/play/wwdc2025/228/), [Android Wi-Fi Aware](https://developer.android.com/develop/connectivity/wifi/wifi-aware).
7. Apple's Network framework can use Apple peer-to-peer networking, which is distinct from Android Wi-Fi Direct. Multipeer Connectivity can discover and transfer among Apple peers; it disconnects sessions when backgrounded. Local network privacy needs usage descriptions and permission handling. There is no general public API for silently enabling Personal Hotspot. [iOS Wi-Fi API overview](https://developer.apple.com/documentation/technotes/tn3111-ios-wifi-api-overview), [Multipeer Connectivity](https://developer.apple.com/documentation/multipeerconnectivity), [local network privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy).
8. Web Bluetooth is a user-selected GATT-client API, not browser-to-browser advertising/scanning or a common media layer. Chrome support does not imply Safari support; WebKit records opposition. An installed PWA does not acquire native radio APIs. A future Android native peripheral could expose a bounded event service, but it needs its own interoperability/security spike. [Chrome Web Bluetooth](https://developer.chrome.com/docs/capabilities/bluetooth), [WebKit positions](https://webkit.org/standards-positions/), [implementation status](https://github.com/whatwg/bluetooth/blob/main/implementation-status.md).
9. HTTPS-to-local-server access is not a universal browser bridge. Chrome's Local Network Access permission begins with fetch/subresources and has a conditional mixed-content exemption for recognized local destinations. Its rollout across WebSocket/WebRTC is evolving. This cannot be generalized to Safari or used to downgrade Saathi's origin. A native hub must provide a trusted secure bridge or exchange WebRTC descriptions rather than assume an arbitrary HTTP server is reachable from every PWA. [Chrome Local Network Access](https://developer.chrome.com/blog/local-network-access).
10. Service workers and IndexedDB provide offline application/storage primitives on secure origins. Cache only the public shell/assets; private sessions, donor bearer links and authenticated API responses need separate handling. Storage can fail or be evicted. Persistent-storage requests, visible save failures, export and user-controlled cleanup are required; no browser can promise permanent storage after uninstall, eviction or user deletion. Home-screen WebKit storage policies differ from an ordinary tab. [PWA offline data](https://web.dev/articles/pwa/offline-data), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/), [WebKit service workers](https://webkit.org/blog/8090/workers-at-your-service/).
11. Browser tabs/PWAs and native applications can be suspended. Service workers cannot keep a WebRTC call or nearby discovery running indefinitely. Periodic/background sync is permission/engagement/platform dependent; a foreground retry path is mandatory. Android BLE connections end if the process is killed; foreground services have launch restrictions. [Chrome background sync](https://developer.chrome.com/docs/capabilities/periodic-background-sync), [Android BLE background](https://developer.android.com/develop/connectivity/bluetooth/ble/background).

The 20 July 2026 Nearby announcement schedules removal of automatic radio enablement for late 2026. The Android probe checks enabled Wi-Fi/Bluetooth and directs the tester to system settings rather than relying on the SDK to toggle them. Apps targeting Android 17/API 37 also need the new local-network permission for applicable LAN operations; the S24 probe targets API 36 and does not claim target-37 validation. [Nearby radio changes](https://developer.android.com/blog/posts/upcoming-changes-to-the-nearby-connections-api), [Nearby permissions](https://developers.google.com/nearby/connections/android/get-started), [Android local-network permission](https://developer.android.com/privacy-and-security/local-network-permission).

## Platform capability matrix

New private chat is a development/QA preview, not a browser feature. Only one peer session is live per adapter; persisted contacts/history do not constitute a live full mesh. Complete new-chat internet-loss transitions, three-native-peer relay, range/battery/lock tests and iOS remain unverified. ## Candidate comparison

The [physical S24/tablet record](benchmarks/samsung-s24-tablet-nearby.json) now supplements the research matrix. It covers the isolated Nearby probe, not native domain integration or any browser/native bridge. The probe uses `ConnectionType.BALANCED`; Google documents that this policy may adjust existing Wi-Fi/Bluetooth connections as needed. The probe requires both radios already enabled and does not call silent radio-toggle APIs. Future production policy must account for preserving the user's existing network. The SDK's selected radio was not recorded. [Connection type reference](https://developers.google.com/android/reference/com/google/android/gms/nearby/connection/ConnectionType).

| Design                                            | Strength                                                                      | Material problem                                                         | Decision                                          |
| ------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| BLE for everything                                | Low-bandwidth discovery/events                                                | Browser asymmetry, no credible video/media throughput, background limits | Reject as universal layer                         |
| WebRTC for everything                             | Browser/native common live data/media APIs                                    | No discovery, no durable events, IP path required                        | Use for paired live communication, not durability |
| Nearby for everything                             | Native radio selection and files                                              | No browser API, GMS dependency; no common browser media path             | Native candidate, hardware gate                   |
| Wi-Fi Direct for everything                       | Android direct bandwidth                                                      | iOS incompatibility and browser limitations                              | Android candidate only                            |
| Wi-Fi Aware everywhere                            | Modern standardized local IP networking                                       | OS/device coverage, pairing interoperability not measured                | Native candidate, feature-detected and gated      |
| Durable signed events + independent live sessions | Offline usefulness, carrier independence, server validation, composable paths | Requires explicit trust and receipt rules                                | Chosen architectural foundation                   |

## Spike protocol and measurement plan

The reproducible workstation spike is `pnpm spike:nearby`. It must use **two independent Chromium processes**, no STUN/TURN, out-of-band description copying, blocked internet HTTP, real data channels, real media negotiation with explicitly synthetic devices, checksum-verified bounded bulk data, and reconnection. Output includes browser version, scope, connection success/time, RTT distribution, throughput and media packet counters. It cannot measure radio range or phone battery.

For the owner's Android devices, record model/OS/Chrome version and run foreground tests on same Wi-Fi, tethering, local-only hotspot, Direct/Aware/Nearby candidates, denied permissions, no internet, server outage/return, out-of-range return, background, screen lock and battery saver. Use two phones; optionally a third for A → B → C store-and-forward. Record success out of 20, median/p95 pairing/RTT, verified bytes/second at several distances, reconnection behavior and battery %/hour with a baseline. Do not fill unmeasured cells with estimates. Native and iPhone combinations stay gated.
